# 08. Сборка, тесты и релиз

> Как собрать демон, прогнать тесты и выпустить новую версию. Как готовый бинарник
> попадает на серверы панели — см. [07. Интеграция](07-integration.md#установка-и-обновление-бинарника).

## Требования

- **Go ≥ 1.21** (модуль `github.com/Vateron-Media/XC_VM_Fanout`, см. `go.mod`).
- Внешних C-зависимостей нет: сборка идёт с `CGO_ENABLED=0` → **статический бинарник**,
  работающий на любом Linux-дистрибутиве.
- Для работы (не сборки) на не-mp2t источниках нужен `ffmpeg` на целевой машине.

## Разработка

```bash
go run ./cmd/xc_fanout -h   # список флагов
go vet ./...                # статический анализ
```

## Тестирование

Тесты лежат рядом с кодом (`*_test.go`) в каждом внутреннем пакете. Основные команды:

```bash
go test ./...                       # все юнит-тесты
go test -race ./...                 # с детектором гонок (перед релизом — обязательно)
go test -cover ./...                # покрытие по пакетам (в % операторов)
go test -v ./internal/server -run TestOverlay   # один пакет / один тест, подробно
```

Набор быстрый (секунды), не требует сети, ручной настройки сокетов или запущенного
демона — каждый тест поднимает ровно то, что ему нужно, в процессе.

### Что покрывает каждый пакет

| Пакет | Что проверяют его тесты |
|-------|-------------------------|
| `hub` | Корректность фан-аута (все подписчики получают идентичный поток байт), сброс медленного подписчика, snapshot/unsubscribe. |
| `tsjoin` | Разбор чистого входа (PAT/PMT + keyframe) и перемотку prebuffer-кольца. |
| `hlsseg` | Нарезку сегментов по keyframe, скользящее окно, вывод плейлиста. |
| `hlscrypt` | Round-trip шифрования сегментов AES-128-CBC. |
| `ingest` | Выравнивание по 188-байтным пакетам через границы чтения. |
| `puller` | Классификацию источника (прямой mp2t vs ремукс ffmpeg), аргументы холодного старта ffmpeg, переподключение и всплытие ошибок ffmpeg (см. ниже). |
| `server` | HTTP-поверхности целиком: control API (register / ingest / signal / probe), отдачу live-TS и HLS, учёт подключений и скоростей, жнец idle-stop, снапшот debug-статистики и отдельный сброс залипшего зрителя (`serve_live_stall_test.go`). |
| `dlog` | Переключение дебаг-лога и молчание при выключенном режиме. |

Синтетический MPEG-TS на вход берётся из хелпера `internal/tsfixture` (собранные вручную
пакеты PAT/PMT/keyframe), поэтому большинство тестов — чистые и детерминированные, без внешних утилит.

### Как тестируются пути ffmpeg

ffmpeg проверяется двумя способами — намеренно:

- **Фейковый ffmpeg** — крошечная shell-заглушка, записанная во временную папку и переданная
  как путь к бинарю ffmpeg. Она делает ветку детерминированной: happy-path ремукса, форсированный
  ненулевой выход (проверяем, что сбой всплывает, а не проглатывается как чистое завершение потока),
  отмена по контексту, которая *не* должна считаться ошибкой, и ветки оверлея — мягкий откат /
  отключён / не удалось стартовать.
- **Реальный системный ffmpeg** — перекодирование оверлея с drawtext прогоняется целиком на
  настоящем `ffmpeg` машины: тест синтезирует реальный H.264 MPEG-TS через `lavfi` и выжигает
  настоящий баннер системным TTF-шрифтом, затем проверяет, что результат — валидный изменённый
  поток. Тест **автоматически пропускается** (с записью в лог), если `ffmpeg` или известный шрифт
  отсутствуют, и **пишет в лог, какой бинарь и шрифт использованы**, если есть — так по прогону
  всегда видно, был ли реальный путь перекодирования выполнен или пропущен, а не «молча прошёл».

Дебаг-лог в тестах выключен; тест, которому нужно проверить вывод лога, включает его и
перехватывает writer лога (шаблон — в `internal/dlog/*_test.go`).

### End-to-end стенд

Помимо юнит-тестов, [`test/`](../../test/) — самодостаточный **end-to-end стенд** (отдельный
Go-модуль, поэтому он никак не влияет на `go test ./...` в корне): фейковый origin-сервер источника
плюс реальный демон, связанные через Docker Compose, покрывающие все режимы работы — прямой pull,
ремукс HLS, failover, off-air, push/ingest, шифрованный HLS, idle-stop по grace, телеметрию
скоростей, вытеснение залипшего зрителя и teardown. Как запускать — см. [`test/README.md`](../../test/README.md).

## Выпуск версии

Номер версии живёт в одном месте — в файле [`VERSION`](../../VERSION) в корне репозитория.
Всё остальное берёт его оттуда, поэтому при выпуске правится только этот файл.

```bash
# 1. Поднимите номер версии — единственный источник правды
echo 0.9.1 > VERSION                        # или отредактируйте VERSION вручную
VERSION="$(cat VERSION)"

# 2. Соберите артефакты. Без аргумента release.sh читает VERSION;
#    с аргументом — сам записывает его в VERSION и использует.
./release.sh                                # == ./release.sh "$VERSION"

# 3. Закоммитьте и поставьте тег той же версией
git commit -am "release $VERSION"
git tag "$VERSION" && git push --tags        # тег БЕЗ префикса "v" — соглашение проекта
```

Что делает `release.sh`:

1. берёт версию из аргумента или из `VERSION` (`VERSION="${1:-$(cat VERSION)}"`);
2. прогоняет `go test ./...`;
3. собирает статические бинарники под архитектуры в `dist/xc_fanout-linux-*`;
4. считает контрольные суммы `dist/SHA256SUMS`.

Версия штампуется в бинарник при сборке через `-ldflags "-X main.version=…"`, поэтому
`xc_fanout -version` печатает именно версию из `VERSION` (панель по ней решает, нужно ли
обновляться).

## Что происходит после push тега

Push тега вида `[0-9]*` (значение из `VERSION`) триггерит workflow
[`.github/workflows/release.yml`](../../.github/workflows/release.yml):

1. checkout всей истории с тегами (`fetch-depth: 0`), установка Go 1.21;
2. `./release.sh "${GITHUB_REF_NAME}"` — пересборка бинарников и контрольных сумм;
3. генерация changelog — коммиты между предыдущим и текущим тегом собираются в тело релиза;
4. публикация ассетов (`dist/xc_fanout-linux-*` и `dist/SHA256SUMS`) на **GitHub Release**
   через `softprops/action-gh-release` с этим changelog в описании.

### Changelog

Описание каждого релиза собирается автоматически из истории git — списком коммитов
между предыдущим и текущим тегом (`--match '[0-9]*'` пропускает нерелизные теги):

```bash
PREV=$(git describe --tags --abbrev=0 --match '[0-9]*' "$VERSION^")
git log --no-merges --pretty='- %s (%h)' "$PREV..$VERSION"
```

Поэтому релизы «живые» без ручного ведения CHANGELOG: осмысленные сообщения коммитов
(`feat:`, `fix:`, `docs:` …) сразу становятся changelog на странице GitHub Release.

Альтернатива вручную (GitHub сгенерирует заметки сам):

```bash
gh release create "$VERSION" dist/* --generate-notes
```

## Соглашения проекта

- **Теги версий — без префикса `v`** (`0.7.0`, не `v0.7.0`). Workflow слушает шаблон
  `[0-9]*`, и `release.sh` печатает сообщения под этот же формат.
- **Бинарники не коммитятся** в дерево — `dist/` в `.gitignore`; распространение только
  через ассеты Release.
- **Источник правды — версия в бинарнике.** Панель читает её через `-version` и сверяет
  с последним тегом релиза.
