# 04. Внутренние механизмы

> Как устроена «начинка»: захват источника, выравнивание пакетов, fan-out TS,
> «чистый вход» и prebuffer, HLS-нарезка и шифрование. Общая картина — в
> [02. Архитектура](02-architecture.md).

Немного контекста про формат. **MPEG-TS** — это поток из пакетов фиксированной длины
**188 байт**, каждый начинается с байта-синхронизации `0x47`. Внутри — служебные таблицы
(**PAT** — список программ, **PMT** — состав программы: какие PID видео/аудио) и
собственно видео/аудио, разложенные по PID. Чтобы плеер начал показывать картинку с
середины потока, ему нужны PAT, PMT и **видео-ключкадр** (keyframe / random access point).
Почти вся «начинка» демона крутится вокруг этих фактов.

## Точка входа данных — `Stream.Publish`

Всё, что демон получает от источника, входит в поток через единственный метод
[`Publish`](../../internal/server/server.go):

```
Publish(chunk):
    если chunk непустой → запомнить время (lastData)   // метка живости для off-air
    Hub.Publish(chunk)                                 // в TS fan-out
    Segmenter.Feed(chunk)                              // в HLS
```

Это единственное место, где данные «раздваиваются» на TS-раздачу и HLS. Метка `lastData`
потом читается статусом (`GET /streams/<id>`) для определения off-air.

## Захват источника — `puller`

> **Важно: `puller` работает ТОЛЬКО для proxy-стримов** (`direct_proxy=1`). У proxy
> нет панельного ffmpeg (это passthrough — без транскода/лого), поэтому источник
> тянет сам демон. **Обычные (non-proxy) стримы демон получает НЕ пуллером, а через
> `ingest`** — это уже подготовленный вывод панельного ffmpeg, который тот отдаёт
> вторым выходом `-f tee` (один ffmpeg → и on-disk HLS, и демон); см.
> [05, режимы питания](05-lifecycle.md#три-режима-питания-потока). Поэтому «mp2t
> напрямую без ffmpeg» ниже — исключительно про **proxy-passthrough**, а не про
> обычные стримы: для них демон всегда берёт вывод ffmpeg, а не прямую ссылку.

[`puller.Run`](../../internal/puller/puller.go) тянет источник, пока поток кому-то нужен,
и **переподключается с экспоненциальным backoff** при обрыве: пауза растёт `1с → 2 → 4 → 8с`
(потолок 8 с), сбрасывается при отмене.

На каждой попытке перебираются `URLs` по порядку, и для каждого делается **проба
(`probe`)** — открывается GET-запрос (с `User-Agent`/`Cookie`/`Proxy`, TLS без проверки
сертификата, **без таймаута** — поток долгоживущий) и смотрится `Content-Type` ответа:

- **`video/mp2t`** → байты **стримятся напрямую** (`ingest.Copy`), без ffmpeg — это
  самый дешёвый путь;
- **любой другой** (HLS-плейлист и т. п.) → запускается **ffmpeg**, который ремуксит
  источник в MPEG-TS.

Это порт логики `ProxyCommand::getActiveStream` из легаси-панели.

### Вызов ffmpeg

Когда источник не является готовым mp2t, `runFfmpeg` запускает (повторяя инвокацию из
`ProxyCommand.php`):

```
ffmpeg -copyts -vsync 0 -nostats -nostdin -hide_banner -loglevel quiet -y
       -user_agent <ua> [-headers "Cookie: …"] [-http_proxy http://host:port]
       -i <url> -map 0 -c copy -mpegts_flags +initial_discontinuity
       -pat_period 2 -f mpegts -
```

Ключевое: `-c copy` — **без перекодирования**, только переупаковка контейнера в TS
(дёшево по CPU). stdout ffmpeg читается тем же `ingest.Copy` и подаётся в `Publish`.

## Выравнивание пакетов — `ingest`

[`ingest.Copy`](../../internal/ingest/ingest.go) читает источник и вызывает `publish`
**чанками, кратными 188 байтам**. Если очередное чтение оборвалось на середине пакета,
«хвост» переносится к следующему чтению — так все парсеры ниже (join, сегментатор)
всегда получают только целые TS-пакеты. Размер чтения задаётся флагом `-chunk`
(по умолчанию 12032; округляется вниз до кратного 188).

Один и тот же `ingest.Copy` используется в трёх местах: прямой mp2t-источник, вывод
ffmpeg, и push-режим (данные из ingest-сокета).

## Fan-out TS — `hub`

[`Hub`](../../internal/hub/hub.go) — точка раздачи одного потока множеству подписчиков.
Одна `Hub` на поток.

- **`Publish(chunk)`**: **копирует** чанк (чтобы источник мог переиспользовать буфер),
  сворачивает его в join-состояние (см. ниже) и **неблокирующе** рассылает всем
  подписчикам через буферизованные каналы.
- **Медленный подписчик отбрасывается.** У каждого подписчика буфер на `subQueue = 256`
  чанков. Если он переполнен (зритель не успевает вычитывать) — подписчик закрывается и
  удаляется. Так один тормозящий зритель **никогда не застопорит источник или других**.
- **`Subscribe(prebufMS)`**: под одним мьютексом одновременно снимает snapshot истории и
  регистрирует подписчика. Атомарность важна: живой хвост продолжается ровно там, где
  кончился snapshot — **без разрыва и без дублирования**.

### Защита от «залипших» зрителей

Отбрасывание по переполнению буфера ловит не все случаи. Если зритель совсем перестал
читать сокет, но **не закрыл соединение** (свёрнутый плеер, оборвавшийся мобильный
канал), его OS-буфер отправки заполняется, и системный вызов записи блокируется
**навсегда** — ни отбрасывание hub’ом, ни отмена HTTP-контекста не прерывают уже
начавшуюся запись.

Решение в [`serveLive`](../../internal/server/server.go): каждая запись зрителю
ограничивается **дедлайном** `-write-timeout` (по умолчанию 15 с). Залипшая запись
превращается в ошибку, срабатывают отложенные `detach`/`removeConn`, и `fanout_sync`
может закрыть строку `lines_live`. Здоровый realtime-зритель копит не больше ~1 с
отставания в секунду, так что дедлайн срабатывает только на реально мёртвых соединениях.

## «Чистый вход» и prebuffer — `tsjoin`

Проблема: зритель подключается к живому потоку в произвольный момент. Если начать лить
ему байты «с текущего места», его плеер увидит середину видеокадра без PAT/PMT и без
ключкадра — и не покажет ничего. Нужен «чистый вход».

[`tsjoin.State`](../../internal/tsjoin/tsjoin.go) честно **разбирает структуру MPEG-TS**
(а не матчит по фиксированным смещениям, как легаси `ProxyCommand`) и держит ровно то,
что нужно новому зрителю для старта:

- последний **PAT** и последний **PMT** (PID PMT вычисляется из PAT);
- **кольцо GOP’ов** — блоков «от ключкадра до следующего ключкадра», каждый помечен
  временем по часам PCR (90 кГц).

Как это работает:

- при `random_access_indicator` (ключкадр) открывается новый GOP; между ключкадрами
  пакеты дописываются в текущий GOP;
- `prune()` выбрасывает старые GOP’ы: по **длительности** (потолок `-prebuffer-max`
  секунд, если PCR парсится) или по **байтовому бэкстопу** (~24 Мбит/с оценка — на
  случай, если PCR не читается), чтобы кольцо не росло без предела;
- **`Snapshot(reqMS)`** собирает то, что отдаётся зрителю до живого хвоста:
  - `reqMS = 0` (или поток без PCR) → `PAT + PMT + только текущий GOP` — минимальный
    чистый вход;
  - `reqMS > 0` → кольцо перематывается к ключкадру ~N секунд назад, и зритель получает
    больше истории, чтобы его плеер стартовал с уже заполненным кэшем.

Это повторяет `client_prebuffer` из легаси `live.php`, который передача через X-Accel
иначе обходит стороной. Клиент задаёт желаемый prebuffer параметром `?prebuffer=` в
[URL `/live/<id>`](03-endpoints.md#get-liveid--живой-ts).

## HLS в памяти — `hlsseg`

[`Segmenter`](../../internal/hlsseg/hlsseg.go) превращает живой TS в HLS **целиком в
оперативной памяти** — ничего не пишется на диск. Это заменяет старый ffmpeg `-f hls`,
писавший `.ts`/`.m3u8` в tmpfs.

Как режет:

- `Feed` парсит пакеты: находит PAT/PMT, по PMT определяет **видео-PID** (H264, HEVC,
  MPEG-1/2, MPEG4, VC-1 — по `stream_type`);
- **новый сегмент нарезается на видео-ключкадре**, когда с прошлого разреза прошло не
  меньше `-hlstarget` секунд (время считается по PTS с учётом 33-битного переполнения);
- каждый сегмент начинается с `PAT + PMT + ключкадр`, чтобы быть самодостаточным;
- держится **скользящее окно** из `-hlswindow` последних сегментов; старые ротируются
  (их номера потом отдают `404`);
- есть жёсткий предохранитель `maxSeg = 16 МБ` на сегмент (аварийный разрез без ключкадра,
  если поток «сломан»).

`Playlist()` рендерит стандартный `#EXTM3U` версии 3 с `EXT-X-TARGETDURATION`,
`EXT-X-MEDIA-SEQUENCE` и строками `#EXTINF`; URI сегментов — `<seq>.ts`.

## Шифрование HLS — `hlscrypt`

[`hlscrypt.EncryptCBC`](../../internal/hlscrypt/hlscrypt.go) шифрует HLS-сегменты
**AES-128-CBC + PKCS#7**, байт-в-байт совместимо с PHP-панелью:
`openssl_encrypt(data, "aes-128-cbc", key, OPENSSL_RAW_DATA, iv)`.

- Один фиксированный `key`+`iv` на поток (файлы панели `<id>_.key` / `<id>_.iv`).
- Ключ/IV передаются демону в теле `/streams` или `/ingest` (hex, по 16 байт).
- Наличие ключа объявляется строкой `#EXT-X-KEY` в плейлисте (её формирует панель).
- Шифруются **только HLS-сегменты**; live TS fan-out (`/live/<id>`) всегда plain.
