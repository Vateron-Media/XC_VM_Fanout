# 06. Параметры и конфигурация

> Что демон потребляет на входе. Начиная с **0.11.1** это приходит из **двух** мест:
> **флаги командной строки** (размещение, идентичность, дебаг — задаются один раз при
> запуске) и **JSON-файл конфигурации** (операторская настройка — размеры буфера,
> таймауты, HLS — редактируется панелью и применяется на лету, без перезапуска). Точка
> входа — [`cmd/xc_fanout/main.go`](../../cmd/xc_fanout/main.go).

Исторически (≤ 0.10.0) у демона **не было конфиг-файла** и каждая настройка была флагом
запуска. Проблема: панель никогда не задавала эти флаги, поэтому значение вроде глубины
prebuffer или окна HLS нельзя было изменить без пересборки. В **0.11.1** операторская
настройка переехала в JSON-файл, который редактирует панель и опрашивает демон; флаги,
несшие эти настройки, были упразднены (см. [Миграция с 0.10.0](#миграция-с-0100) ниже).

Динамика (какие потоки обслуживать) по-прежнему приходит в рантайме через
[управляющий API](03-endpoints.md#управляющая-поверхность-только-для-php).

## Флаги командной строки

Флаги задают, чем демон *является* (его сокеты, идентичность, дебаг), а не настраиваемые
числа. Они фиксированы на всё время жизни процесса.

| Флаг | По умолчанию | Назначение |
|------|--------------|------------|
| `-sock` | `/home/xc_vm/bin/xc_fanout/sockets/http.sock` | Клиентский unix-сокет (сюда ходит nginx/зрители). |
| `-ctl` | `""` (выкл.) | Управляющий unix-сокет (только PHP). Пустой = управляющего API нет. |
| `-ingestdir` | `<каталог -sock>/ingest` | Каталог per-stream push-сокетов (для ingest-режима). |
| `-config` | `/home/xc_vm/bin/xc_fanout/config.json` | Путь к JSON-файлу операторской настройки (см. [Конфиг-файл](#конфиг-файл)). Самосоздаётся с дефолтами, если отсутствует; недостающие ключи дозаполняются; опрашивается и применяется на лету. Пусто = файл отключён (используются встроенные дефолты). |
| `-config-interval` | `60` | Секунды между перечитываниями конфиг-файла. Файл перечитывается, только когда меняется его mtime. |
| `-ffmpeg` | `ffmpeg` | Путь к бинарнику ffmpeg (для ремукса не-mp2t источников и оверлея `drawtext` «отправить сообщение»). Для работы оверлея нужен билд с фильтром `drawtext`. |
| `-font` | `""` (оверлей выкл) | Путь к `.ttf`-шрифту для оверлея «отправить сообщение». Пусто или ffmpeg без `drawtext` — оверлей отключён (сигналы становятся no-op). |
| `-debug` | `false` | Подробный дебаг-лог: демон рассказывает про активность потоков/пуллера/зрителей/HLS/ingest/монитора плюс периодический снимок состояния по каждому потоку. Также включается через `XC_FANOUT_DEBUG=1`. См. [«Дебаг-режим»](#дебаг-режим) ниже. |
| `-debug-cats` | (все) | Ограничить дебаг-лог этими категориями через запятую (`puller,monitor`). Также задаётся как `XC_FANOUT_DEBUG=puller,monitor`. |
| `-debug-stats` | `5` | Секунды между периодическими снимками состояния потоков в дебаг-режиме (`0` отключает только снимок; лог событий остаётся включённым). |
| `-version` | — | Напечатать версию и выйти. |

### Флаги режима «launch / test»

Для изолированного тестирования — подать один поток прямо при старте, без control API:

| Флаг | Назначение |
|------|------------|
| `-id` | Идентификатор потока, который подать при старте (пусто = только обслуживать). |
| `-source` | Источник(и) для `-id`, через запятую (pull-режим). |
| `-in` | Входной файл для `-id`, либо `-` для stdin. |
| `-ua` | User-Agent источника. |
| `-proxy` | HTTP-прокси источника `host:port`. |
| `-cookie` | Значение заголовка `Cookie` для источника. |

`-source` и `-in` взаимоисключающие: первый — тянуть по URL, второй — читать из файла/stdin.

## Конфиг-файл

Операторская настройка живёт в маленьком JSON-файле (`-config`, по умолчанию
`/home/xc_vm/bin/xc_fanout/config.json`), которым владеет
[`internal/config`](../../internal/config/config.go). Админ правит значения в панели;
панель пишет их в этот файл; демон опрашивает его и применяет изменения **в рантайме —
без перезапуска, без сброса зрителей**.

### Самоподдерживающийся

Файл никогда не нужно создавать или мигрировать вручную:

- **Отсутствует** → демон пишет его со встроенными дефолтами
  ([`internal/defaults`](../../internal/defaults/defaults.go), константы `Cfg*`), так что
  свежая нода стартует с реального, редактируемого файла вместо пустоты. Это работает не
  только при старте: если файл **удалён во время работы демона**, следующий опрос его
  пересоздаёт — пересохраняя значения, которые сейчас в памяти (так что удаление никогда
  не сбрасывает живую настройку молча), либо встроенные дефолты, если ничего ещё не
  известно.
- **Не хватает ключа** → демон дозаполняет этот ключ его дефолтом **и переписывает файл**,
  так что файл на диске всегда несёт полную текущую схему демона. **Старая** панель,
  пишущая лишь часть, никогда не заставит демон упасть, а ключ, который добавил **новый**
  демон, появится в файле (со своим дефолтом), чтобы панель его подхватила.
- **Битый** → демон сохраняет работающие значения и **не** переписывает файл (это может
  быть оборванная посередине запись или ручная правка в процессе); следующий опрос
  повторит попытку. Раздача никогда не ломается из-за плохого конфига.

Записи **атомарны** (временный файл + rename), так что читатель — опрашивающий демон или
параллельная запись панели — никогда не видит наполовину записанный файл.

### Опрашивается и применяется на лету

Демон перечитывает файл каждые `-config-interval` секунд, но только когда **mtime** файла
изменился с прошлой проверки (stat, а не полный разбор, на тихом тике). Изменение
применяется к **существующим** потокам на месте в пределах одного опроса:

- **prebuffer-кольцо** и **окно HLS** сразу сжимаются и освобождают память;
- `write_timeout_sec` / `source_insecure` становятся атомарными (их читают на горячих путях);
- `chunk_bytes` / `max_gop_bytes` вступают в силу для **вновь создаваемых** потоков.

Ни один поток не сбрасывается и ни один зритель не отключается при изменении конфига.

### Ключи

Каждое значение проверяется (зажимается) при загрузке, так что опечатка в панели или
правка файла руками никогда не загонят демон в патологическое состояние.

| Ключ | По умолчанию | Диапазон | На что влияет |
|------|--------------|----------|---------------|
| `prebuffer_max_sec` | `40` | `0…120` | Размер буфера/кольца на поток (секунды TS-истории). Это **и есть** буфер — он задаёт и TS-prebuffer, и глубину HLS. |
| `default_prebuffer_sec` | `0` | `0…120` | Фолбэк-«всплеск» на входе для зрителя **только**, когда запрос `/live/` не несёт `?prebuffer=`. `0` = демон не навязывает ничего (только текущий GOP). См. [Prebuffer на зрителя](#prebuffer-на-зрителя). |
| `hls_target_sec` | `6` | `1…30` | Целевая длительность HLS-сегмента (секунды). Реальная длина плавает (режем по ключкадрам). |
| `hls_window` | `6` | `1…20` | Сколько HLS-сегментов перечисляет плейлист — **потолок отображения**, а не драйвер кольца. |
| `grace_sec` | `10` | `1…3600` | Grace простоя для control-управляемых потоков: сколько источник живёт после ухода последнего зрителя (окно рипера). |
| `write_timeout_sec` | `15` | `1…600` | Дедлайн на одну запись live-TS зрителю до сброса залипшего соединения. |
| `chunk_bytes` | `12032` | `188…4 MiB` | Размер чтения источника для потоков, которые тянет демон (выравнивается вниз до кратного 188). |
| `max_gop_bytes` | `10528000` | `188…256 MiB` | Потолок одного блока кольца. Источнику, не давшему ключкадра за столько байт, блок **режется** здесь (см. [Источники без ключевых кадров](04-internals.md#источники-без-ключевых-кадров)). |
| `source_insecure` | `true` | — | Пропускать проверку TLS upstream'а при вытягивании HTTPS-источников. `true`, потому что панель часто тянет upstream'ы с самоподписанными/несовпадающими сертами; поставьте `false`, чтобы требовать валидные сертификаты. |
| `idle_buffer_grace_sec` | `30` | `0…3600` | Окно без зрителей до сжатия кольца (`0` = гейт простоя выключен). См. [Гейт простаивающего буфера](#гейт-простаивающего-буфера). |
| `idle_buffer_ratio` | `0.5` | `0.1…1` | Доля буфера, удерживаемая, пока поток никто не смотрит. HLS всё равно режется из сжатого кольца, так что канал остаётся открываемым. |
| `viewer_idle_timeout_sec` | `30` | `0` или `5…3600` | Отбросить live-TS зрителя, которому столько времени не пришло **ничего** (`0` = никогда). Именно это ограничивает призрака на офф-эйрном потоке: `write_timeout_sec` срабатывает, только пока есть что писать. См. [Защита от залипших и простаивающих зрителей](04-internals.md#защита-от-залипших-и-простаивающих-зрителей). |
| `source_backend` | `auto` | `auto`, `ffmpeg`, `native` | Как **не-mp2t** источник становится MPEG-TS. Ту же настройку панель читает, чтобы выбрать, что запускать для своих супервизируемых потоков. См. [Бэкенд источника](#бэкенд-источника). Сверяется без учёта регистра; неизвестное значение откатывается к `auto`. |
| `supervise` | `false` | `true`, `false` | Принимать live-потоки, которые панель передаёт на супервизию энкодеров. Пишется панелью из её настройки **Fanout Encoder Supervision** и применяется на лету: выключение останавливает новые передачи (`PUT /monitor/<id>` отвечает `501`), но уже супервизируемые потоки продолжают работать. |
| `mem_limit_mb` | `0` (авто) | `0…1 ТиБ` | Явный потолок (МиБ) для мягкого лимита памяти Go. `0` — вывести его из лимита cgroup, иначе из доли RAM машины. См. [Бюджет памяти](#бюджет-памяти). |

Минимальный файл, который демон пишет на свежей ноде:

```json
  "hls_window": 6,
  "grace_sec": 10,
  "write_timeout_sec": 15,
  "chunk_bytes": 12032,
  "max_gop_bytes": 10528000,
  "source_insecure": true,
  "default_prebuffer_sec": 0,
  "idle_buffer_grace_sec": 30,
  "idle_buffer_ratio": 0.5,
  "viewer_idle_timeout_sec": 30,
  "mem_limit_mb": 0,
  "source_backend": "auto"
}
```

## На что влияют ключевые параметры

### Буфер / кольцо

Начиная с 0.11.1 существует **один** буфер на поток, а не два: выровненное по ключкадрам
TS-кольцо в [`tsjoin`](04-internals.md#чистый-вход-и-prebuffer--tsjoin). `prebuffer_max_sec`
задаёт его размер, а HLS — **вид** поверх него (см.
[ADR 0001](../adr/0001-single-ts-cache-hls-on-demand.md)). Так что это одно число задаёт и
live-TS prebuffer, и то, насколько глубоко может дотянуться окно HLS.

- **`prebuffer_max_sec`** — потолок TS-истории, которую держит поток. Прямо задаёт потолок
  RAM на поток. Должен быть ≥ окна HLS (`hls_window · hls_target_sec`), чтобы HLS дотянулся
  до полной глубины; дефолт 40 с запасом покрывает окно 6×6.
- **`max_gop_bytes`** — предел размера одного блока кольца. В норме недостижим: блоки режутся по
  ключкадрам, а они приходят куда чаще. Он ограничивает источник, у которого ключкадры редки или
  отсутствуют: достижение потолка вынуждает границу блока, и кольцо продолжает катиться, а не
  замерзает. (До 0.11.4 это был порог выбрасывания: всё сверх него отбрасывалось, и поток
  застревал на одном блоке. См.
  [04, «Источники без ключевых кадров»](04-internals.md#источники-без-ключевых-кадров).)
- **`chunk_bytes`** — размер порций чтения источника. Выравнивается вниз до кратного 188.

### Гейт простаивающего буфера

Чтобы простаивающие каналы не держали полный буфер без аудитории, у потока с **отсутствием
live-зрителя и без касаний зрителем** (TS-подключение или HLS-запрос) в течение
`idle_buffer_grace_sec` его кольцо сжимается до `prebuffer_max_sec × idle_buffer_ratio`
проходом рипера и накачивается обратно до полного буфера в тот же миг, как зритель
возвращается. HLS **продолжает нарезаться** из сжатого кольца (с полом `2 · hls_target`,
чтобы оставался хотя бы один сегмент), так что плейлист простаивающего HLS-канала остаётся
непустым и открывается сразу. Поставьте `idle_buffer_grace_sec = 0`, чтобы выключить гейт
целиком. См. [05. Жизненный цикл](05-lifecycle.md) и
[ADR 0001](../adr/0001-single-ts-cache-hls-on-demand.md).

### Prebuffer на зрителя

Глубина «всплеска» на входе, которую зритель получает при подключении, — это решение
**панели**, а не демона: панель знает, клиент это или рестример, и передаёт выбранную
глубину в параметре `?prebuffer=<сек>` внутреннего URL `/live/<id>`. Демон чтит это
значение **как есть, включая явный `0`** (= только текущий GOP). `default_prebuffer_sec` —
фолбэк, используемый **только**, когда запрос вовсе не несёт `?prebuffer=`; его дефолт `0`
означает, что демон сам ничего не навязывает.

### Тайминги жизненного цикла

- **`grace_sec`** — насколько «инерционен» источник. Больше значение = источник дольше
  живёт после ухода зрителей (быстрее подхват при возврате, но дольше висит впустую). Рипер
  тикает каждые `grace/2`. См. [05. Жизненный цикл](05-lifecycle.md).
- **`write_timeout_sec`** — порог сброса «залипшего» зрителя. Меньше = быстрее чистим
  мёртвые соединения, но выше риск задеть медленного, но живого. 15 с — с запасом, т. к.
  здоровый realtime-зритель копит ≤ 1 с отставания в секунду. См.
  [04, «Защита от залипших зрителей»](04-internals.md#защита-от-залипших-и-простаивающих-зрителей).
- **`viewer_idle_timeout_sec`** — порог сброса **простаивающего** зрителя, т. е. такого, которому
  вообще ничего не отправляется. `write_timeout_sec` покрывает зрителя, который не хочет
  *читать*; этот — поток, которому нечего *писать*. Должен с запасом превышать провал источника
  (backoff переподключения упирается в 8 с плюс холодный старт ffmpeg), иначе восстанавливающийся
  источник стоит зрителям соединения; `0` выключает отбрасывание и возвращает поведение до
  0.11.4, когда такой зритель висел вечно.

### Бэкенд источника

Источник, который и так отдаётся как `video/mp2t`, стримится напрямую и этой настройки не касается
вовсе. Всё остальное — HLS-плейлист, udp-фид — нужно преобразовывать, и здесь выбирается как:

| Значение | Поведение |
|----------|-----------|
| `auto` (по умолчанию) | Преобразовывать **внутри процесса** там, где [`nativesrc`](04-internals.md#нативное-преобразование--nativesrc) может, и через **ffmpeg** для всего, что он отклонит. |
| `ffmpeg` | Всегда запускать ffmpeg. Поведение до 0.12, оставленное как аварийный выключатель. |
| `native` | Только нативно: источник, который нативный ридер отклонил, **падает**, а не откатывается. Отклонённый источник тогда — мёртвый канал, а не чуть более дорогой, так что это для узла, чьи источники заведомо подходят. |

`auto` стоит по умолчанию, потому что откат делает его строго безопаснее `ffmpeg`: всё, что
нативный ридер не возьмёт, идёт ровно по тому же конвейеру, что и раньше, а частый случай (HLS с
TS-сегментами) перестаёт стоить по дочернему процессу на поток. Выигрыш — на один процесс ~27 МБ
меньше на каждый прокси-поток плюс отсутствие запуска процесса при каждом подключении по
требованию.

**Панель использует те же три значения для своих потоков.** При включённой супервизии поток,
которому достаточно копирования, производит нативный ремуксер (`xc_fanout remux`) вместо ffmpeg
при `auto` и `native`; `auto` вдобавок даёт ему команду ffmpeg панели как запасную для
источников, которые ремуксер прочитать не может, `native` — нет, а `ffmpeg` оставляет ffmpeg.
Какую команду запускать, решает и собирает панель; сам демон никогда её не выбирает.

Значение сверяется без учёта регистра и с обрезкой пробелов, так что `Native` и `" native"`
работают. То, что не называет никакой бэкенд, откатывается к `auto`.

Применяется на лету при перезагрузке конфига и вступает в силу со **следующего** захвата: уже
подключённый поток остаётся на своём пути и подхватит новый при следующем старте захватчика.

> **До 0.13 это было сломано.** Бэкенд впечатывался в поток в момент его регистрации панелью, так
> что перезагрузка конфига доходила до общеузловой настройки и на этом останавливалась: каждый уже
> известный поток бесконечно сохранял свой старый бэкенд — через idle-остановки и перезапуски — пока
> панель случайно не перерегистрирует его. Оператор, переключивший узел на `native`, не видел
> никаких изменений и не мог выяснить почему. Теперь значение определяется при старте захватчика —
> ровно так, как этот абзац утверждал всегда.

**Переопределение на поток.** `PUT /streams/<id>` принимает поле
[`backend`](03-endpoints.md#put--post-streamsid--регистрация-pull-источника), закрепляющее один
канал, — так отдельный проблемный источник можно принудительно отправить в ffmpeg, не меняя узел.
Неизвестное значение там игнорируется (поток берёт общеузловую настройку), а не закрепляет
несуществующее.

### Бюджет памяти

Демон выдаёт рантайму Go **мягкий** лимит памяти (`GOMEMLIMIT`): это потолок, а не резервирование
— GC ужесточается лишь по мере приближения к нему, и рабочий набор, идущий сильно ниже, его не
чувствует. Бюджет берётся по порядку:

1. **`mem_limit_mb`**, если задан. Используйте его на общей панельной ноде: вы знаете, как делится
   память между демоном, nginx, MySQL, PHP-FPM и ffmpeg’ами потоков, а демон — нет.
2. **лимит cgroup**, под которым идёт процесс (v2 `memory.max`, затем v1 `memory.limit_in_bytes`),
   — это его собственный бюджет, поэтому забирается **80%**;
3. иначе **физическая RAM** машины, от которой забирается только **50%**: машина общая, и, взяв
   большую её часть, fan-out растёт, пока не начнёт душить те самые процессы, что его кормят.

`GOMEMLIMIT` в окружении перекрывает всё это (тогда демон не ставит ничего). Выбранный лимит и его
источник пишутся в лог при старте, а `mem_limit_mb` переприменяется на лету при перезагрузке
конфига.

### HLS

- **`hls_target_sec`** — целевая длина сегмента (реальная длина плавает, т. к. режем по
  ключкадрам). Влияет на задержку HLS и частоту сегментов.
- **`hls_window`** — сколько последних сегментов перечисляет плейлист. Больше окно = длиннее
  «хвост» для перемотки/догоняющих плееров. Теперь это лишь **потолок отображения**: байты
  на деле держит кольцо (`prebuffer_max_sec`), так что окно больше, чем кольцо может
  вместить, зажимается кольцом.

### Пути и доступ

- **`-sock` / `-ctl` / `-ingestdir`** — размещение unix-сокетов. Демон при старте создаёт
  каталоги, удаляет старые файлы сокетов и слушает с правами `0660`. Если `-ctl` пуст —
  управляющий API не поднимается вовсе (демон работает только на раздачу).

## Что происходит при старте

1. Разбор флагов (`-version` → печать версии и выход).
2. Загрузка конфиг-файла (`-config`): самосоздание с дефолтами, если отсутствует,
   дозаполнение любых недостающих ключей. Пустой `-config` пропускает файл и использует
   встроенные дефолты.
3. Создание `Manager` с итоговой настройкой; запуск опросчика конфига (каждые
   `-config-interval`).
4. Создание каталога ingest-сокетов, запуск рипера.
5. Поднятие клиентского HTTP-сервера на `-sock`; если задан `-ctl` — и управляющего.
6. Если задан `-id` — разовая подача тестового потока.
7. Ожидание сигнала; по `SIGINT`/`SIGTERM` — graceful shutdown (2 с) и удаление сокетов.

## Пример запуска

```bash
# Боевой режим: обе поверхности, источники приходят через control API.
# Настройка берётся из конфиг-файла (самосоздаётся при первом запуске), а не из флагов.
xc_fanout \
  -sock   /home/xc_vm/bin/xc_fanout/sockets/http.sock \
  -ctl    /home/xc_vm/bin/xc_fanout/sockets/control.sock \
  -config /home/xc_vm/bin/xc_fanout/config.json

# Тест одного потока из файла, без control API
xc_fanout -id test -in ./sample.ts

# Тест одного потока с внешнего URL
xc_fanout -id test -source https://example/live.m3u8 -ua "Mozilla/5.0"
```

## Миграция с 0.10.0

Следующие флаги существовали в ≤ 0.10.0 и были **удалены** в 0.11.1. Их значения теперь —
ключи в [конфиг-файле](#ключи), редактируемые из панели и применяемые на лету:

| Упразднённый флаг (≤ 0.10.0) | Теперь (0.11.1) |
|------------------------------|-----------------|
| `-prebuffer-max` | `prebuffer_max_sec` (дефолт поднят `20 → 40`) |
| `-hlstarget` | `hls_target_sec` |
| `-hlswindow` | `hls_window` |
| `-grace` | `grace_sec` |
| `-write-timeout` | `write_timeout_sec` |
| `-chunk` | `chunk_bytes` |
| `-maxgop` | `max_gop_bytes` |
| `-source-insecure` | `source_insecure` |

Новое в 0.11.1 и не бывшее флагом раньше: `default_prebuffer_sec`, `idle_buffer_grace_sec`,
`idle_buffer_ratio` и два флага, управляющие самим файлом — `-config` и `-config-interval`.
При обновлении никаких действий не нужно: при первом запуске демон пишет файл с этими
дефолтами; существующая панель, которая знает лишь старые ключи, продолжает работать (демон
дозаполняет остальное).

## Дебаг-режим

По умолчанию демон почти молчит — логирует только запуск, фатальные ошибки и
переподключения к источнику. Когда нужно увидеть, *что он делает прямо сейчас* и
*где он застрял*, включите дебаг-режим флагом `-debug` (или `XC_FANOUT_DEBUG=1`).
Таймстампы лога переключаются на микросекундную точность, чтобы было видно тайминг
медленного probe, зависшего зрителя или backoff переподключения.

Дебаг-режим озвучивает каждое интересное событие, каждая строка помечена
`[dbg <категория>]`:

| Категория | Что сообщает |
|-----------|--------------|
| `boot` | Версия, pid и итоговая конфигурация при старте. |
| `stream` | Поток создан; пуллер стартует/останавливается (с текущим счётчиком зрителей). |
| `puller` | Старт вытягивания источника, HTTP-статус и content-type каждого probe, какой URL выбран и **как** (прямой mpegts / нативно / ffmpeg, и был ли ffmpeg закреплён или это откат), ошибки probe, чистое завершение источника, backoff переподключения и остановка. |
| `monitor` | Супервизия энкодеров: передача потока, старт/перезапуск с pid, вердикты здоровья, переключения источника, усыновление выжившего — плюс на каждом тике `-debug-stats` по строке на супервизируемый поток: производитель (`cmd` / `fallback` / `adopted`), аптайм и собственный `tick_age` сторожа с тем, что он последним измерил и против каких взведённых порогов. Устаревший `tick_age` означает, что цикл наблюдения застрял, — а на здоровой ноде это выглядит ровно так же, как тишина. |
| `viewer` | Подключение live-TS и одна строка отключения на зрителя с **причиной** — клиент закрыл соединение, отброшен как слишком медленный (буфер хаба переполнен) или запись зависла дольше `write_timeout_sec` — плюс длительность сессии и отданные КБ. |
| `hls` | Отданные сегменты (seq + размер) и аномалии: плейлист запрошен пока идёт разогрев / поток off-air, либо сегмент уже выпал из окна. |
| `ingest` | Поднят push-слушатель, подключение/отключение продюсера. |
| `ctl` | Действия control API: регистрация/снятие, прогрев через probe и его результат. |
| `signal` | Оверлей «отправить сообщение» поставлен в очередь и применён. |
| `reaper` | Idle-остановка control-управляемого потока после окна grace и гейтинг простаивающего буфера (сжатие / восстановление кольца). |
| `stats` | Периодический снимок по каждому потоку (каждые `-debug-stats` секунд): `mode`, `running`, `route`, зрительские `refs`, подписчики хаба `subs`, отслеживаемые `conns`, `data_age` (растущий `data_age` у работающего потока — сигнал **off-air**) и `nokf` (блоки кольца, отрезанные по байтовому потолку за неимением ключкадра: ненулевое значение — источник без точек произвольного доступа, а значит, он никогда не даст HLS-сегментов). |

Два поля в строке `stats` отвечают на вопросы, для которых раньше приходилось читать источник:

- **`mode`** — как поток кормится, а значит, какие правила к нему вообще применимы:
  `pull` (демон сам его тянет), `ingest` (**push** от продюсера — tee ffmpeg или нативный
  ремуксер — так что пуллера у него нет и `source_backend` до него не доходит) или `idle`
  (зарегистрирован, ничего не запущено).
- **`route`** — `<configured>/<actual>`: бэкенд, который потоку велено использовать, и путь,
  которым он реально пошёл (`direct-mp2t`, `native`, `ffmpeg-pinned`, `ffmpeg-fallback`). Они
  расходятся всякий раз, когда нативный читатель отказывается от источника, — а это ровно то, как
  снаружи выглядит «нода настроена на native, а всё ещё плодит ffmpeg». Push-поток показывает `n/a`.

```bash
# Полный дебаг, снимок по потокам каждые 2 с
xc_fanout -sock … -ctl … -debug -debug-stats 2

# Только две подсистемы, которые вы реально ловите
xc_fanout -sock … -ctl … -debug-cats puller,monitor

# То же через окружение (удобно для systemd drop-in)
XC_FANOUT_DEBUG=1 xc_fanout -sock … -ctl …
XC_FANOUT_DEBUG=monitor xc_fanout -sock … -ctl …
```

Выбор категорий важен, когда нода несёт сотни каналов: полное повествование больше, чем кто-либо
способен прочитать, а нужная подсистема тонет в болтовне остальных 499 потоков. `-debug-cats`
берёт верх над окружением, а оно — над `-debug`, так что systemd drop-in, просящий одну категорию,
не расширяется молча из-за `-debug`, который кто-то оставил в командной строке.

Когда дебаг выключен, инструментация стоит одну атомарную загрузку на точку вызова
и ничего не форматирует, поэтому вызовы безопасно оставлять на горячих путях
(публикация каждого чанка, запись каждому зрителю). Фильтруйте вывод по категории
через `grep`, например `journalctl -u xc_fanout | grep '\[dbg viewer'`, чтобы
следить только за оттоком зрителей.
