# 07. Интеграция с панелью XC_VM

> Как демон встроен в систему: кто с ним разговаривает, кто носит байты, как ставится и
> обновляется бинарник. Справочник адресов — в [03. Endpoint’ы](03-endpoints.md).

Демон — не самостоятельный продукт, а нагруженная «мышца» внутри панели XC_VM.
Вокруг него — четыре участника: nginx, PHP-панель, демон `fanout_sync` и механизм
установки бинарника.

## Кто с кем разговаривает

```
                    ┌─────────────── PHP-панель ───────────────┐
                    │  live.php (авторизация, X-Accel)          │
                    │  StreamProcess (регистрация источников)   │
                    │  console.php fanout_binary (установка)    │
                    └───────────────┬───────────────────────────┘
                                    │ control-сокет (-ctl)
                                    │ PUT/GET/DELETE /streams,/ingest,/probe,/signal
                                    ▼
   зритель ──HTTP──► nginx ──X-Accel──► [ xc_fanout ] ──тянет/принимает──► источник
                       ▲   client-сокет (-sock)         │
                       │   /live, /hls                  │ GET /connections
                       └──────────  fanout_sync ────────┘  (реконсиляция зрителей)
```

## nginx — переносит байты наружу

nginx проксирует запросы зрителей на **клиентский сокет** (`-sock`). Ключевой приём —
`X-Accel-Redirect`: `live.php` авторизует зрителя и **отдаёт nginx внутренний URL** вида

```
/xc_fanout/<id>?c=<uuid>&prebuffer=<сек>
```

Именно `/xc_fanout/<id>` эмитит PHP; nginx во внутреннем `location` переписывает этот
путь в даемоновский `/live/<id>` и проксирует на `-sock`. После этого **байты несёт
nginx**, а PHP-процесс освобождается: он принял решение «пускать/не пускать» и вышел.

> ⚠️ Цель X-Accel обязана быть **2-сегментной** (`/xc_fanout/<id>`). Серверный catch-all
> `rewrite ^/(user)/(pass)/(stream)` в nginx срабатывает и на внутренних редиректах — и
> 3-сегментный путь (напр. `/xc_fanout/live/<id>`) он перехватит и разберёт как
> `user=xc_fanout`/`pass=live` → `INVALID_CREDENTIALS`.

**HLS устроен иначе — плейлист через X-Accel НЕ идёт.** Сегменты `X-Accel`-редиректятся
на демон (`segment.php` → внутренний `/xc_fanout_hls/<id>_<seq>`), а вот **плейлист
`index.m3u8` формирует PHP**: `live.php` сам забирает его с клиентского сокета демона
(`FanoutClient::hlsPlaylist`), переписывает относительные `<seq>.ts` в токенизированные
авторизованные URL (`HLSGenerator::tokenizeDaemonPlaylist`, при шифровании добавляет
`#EXT-X-KEY`) и **сам отдаёт** результат. Плейлист опросный и маленький, так что PHP тут
задействован на каждый опрос — из байтового тракта уходят только сегменты.

## PHP-панель — управляет, но не носит видео

PHP ходит на **управляющий сокет** (`-ctl`):

- **Регистрация источников.** Для pull/proxy-канала — `PUT /streams/<id>` с URL,
  User-Agent, прокси, cookie, при необходимости ключом шифрования HLS. Для push-канала —
  `PUT /ingest/<id>` (панельный `StreamProcess` перед запуском ffmpeg-tee потока получает
  путь ingest-сокета).
- **Off-air-детекция.** `GET /streams/<id>` (статус) и `GET /probe/<id>?wait=<ms>`
  (прогрев источника и ожидание данных). Если данных нет — панель показывает страницу
  «not on air», повторяя поведение легаси `startProxy`, но не давая зрителю зависнуть на
  мёртвом источнике.
- **Снятие каналов.** `DELETE /streams/<id>` или `DELETE /ingest/<id>`.
- **Оверлей «отправить сообщение».** Админское действие постит `POST /signal/<uuid>` (через
  `FanoutClient::sendSignal`), ставя в очередь одноразовый баннер `drawtext` одному зрителю; демон
  выжигает его на следующий HLS-сегмент / короткое TS-окно этого зрителя. Заменяет легаси-оверлей из
  байтового тракта PHP, убранный в фазе E.

## fanout_sync — сверяет список зрителей

Под X-Accel PHP **не видит момент отключения зрителя** (соединение держит nginx, а не
PHP). Поэтому строки `lines_live` (учёт активных просмотров) могли бы «зависать»
открытыми.

Решение: `live.php` создаёт строку `lines_live` с `pid=0` и прокидывает зрителю
connection-uuid через `?c=<uuid>`. Демон `fanout_sync` периодически читает
`GET /connections` (список uuid всех активных live-TS зрителей по всем потокам) и
**закрывает строки**, чьих uuid в этом списке уже нет. Демон, со своей стороны, надёжно
детектирует отключение — в т. ч. через сброс «залипших» зрителей по `-write-timeout`
(см. [04](04-internals.md#защита-от-залипших-зрителей)).

> **Закрытие не мгновенное.** Между реальным уходом зрителя и закрытием строки набегает:
> до `-write-timeout` (15 с) — пока демон сбросит залипшее соединение и уберёт uuid из
> `/connections`; + интервал реконсиляции `fanout_sync` (~10 с); при этом строка не
> закрывается раньше connect-grace самого `fanout_sync` (~20 с от создания — защита от
> гонки на подключении). Итог: «призрак» после нечистого разрыва живёт до ~25–35 с, затем
> слот освобождается. При честном закрытии соединения демон убирает uuid сразу, без
> ожидания `-write-timeout`.

## Установка и обновление бинарника

Исходники живут в этом репозитории; **скомпилированные бинарники — ассеты GitHub
Release** (в дерево не коммитятся, `dist/` в `.gitignore`). Панель ставит и обновляет
демон командой:

```
console.php fanout_binary          # установить/обновить до последнего релиза
console.php fanout_binary force     # переустановить ту же версию
```

Что происходит внутри:

1. читается версия установленного бинарника (`xc_fanout -version`);
2. сравнивается с тегом последнего релиза на GitHub;
3. качается ассет под архитектуру машины;
4. проверяется его **SHA-256**;
5. бинарник ставится **атомарно**, а keepalive сервиса перезапускает демон.

> ⚠️ Перезапуск демона (в т. ч. это обновление) **обнуляет его in-memory реестр потоков**.
> pull-потоки восстановятся на следующем зрителе, а вот push/ingest-потоки — нет, пока их
> ffmpeg не перезапустится и заново не вызовет `PUT /ingest`. Детали и способ форсировать
> re-warm — [05, «Перезапуск и восстановление состояния»](05-lifecycle.md#перезапуск-и-восстановление-состояния).

Подробнее про выпуск версий — [08. Сборка и релиз](08-build-release.md).
