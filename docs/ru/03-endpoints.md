# 03. HTTP endpoint’ы

> Полный справочник обоих HTTP-интерфейсов демона. Про то, почему их два и на каких
> сокетах они живут — см. [02. Архитектура](02-architecture.md#две-http-поверхности-на-разных-unix-сокетах).

Демон обслуживает две поверхности:

- **Клиентская** (`-sock`, для nginx/зрителей) — раздача видео.
- **Управляющая** (`-ctl`, только для PHP) — регистрация потоков и статус.

Везде `<id>` — идентификатор потока (строка), под которым он зарегистрирован.

---

## Клиентская поверхность (для nginx)

Роутинг — [`ClientHandler`](../../internal/server/server.go). Сюда nginx проксирует
запросы зрителей, обычно через `X-Accel-Redirect` из `live.php`.

| Метод и путь | Назначение |
|--------------|------------|
| `GET /live/<id>` | Живой MPEG-TS fan-out. |
| `GET /hls/<id>/index.m3u8` | Медиаплейлист HLS. |
| `GET /hls/<id>/<seq>.ts` | HLS-сегмент по номеру. |
| `GET /healthz` | Health-check. |

### `GET /live/<id>` — живой TS

Держит соединение открытым и непрерывно льёт зрителю MPEG-TS. Обработчик —
[`serveLive`](../../internal/server/server.go).

**Query-параметры:**

| Параметр | Тип | Смысл |
|----------|-----|-------|
| `prebuffer` | секунды (целое) | Сколько истории «догнать» на входе. Зажимается потолком `-prebuffer-max` (по умолчанию 20 с). Отсутствие/0 = минимальный чистый вход (только текущий GOP). |
| `c` | uuid | Идентификатор соединения зрителя (его прокидывает `live.php`). По нему `fanout_sync` отслеживает отключение и закрывает строку `lines_live`; с ним же сопоставляется оверлей из очереди [`/signal/<uuid>`](#post-signaluuid--оверлей-отправить-сообщение). |
| `vc` | codec | Видеокодек источника, прокидывается `live.php`. Используется только если для `?c=` активен оверлей «отправить сообщение» — чтобы сохранить кодек на переходном перекодировании; иначе игнорируется. |

**Что происходит при подключении:**

1. Находит поток по `<id>` (иначе `404`).
2. Считает prebuffer из `?prebuffer=`, зажимает потолком.
3. Атомарно снимает «снимок для чистого входа» (PAT/PMT + нужный хвост GOP’ов) и
   подписывается на живой хвост — без разрыва и дублирования.
4. `attach()` — учитывает зрителя и **запускает puller при первом зрителе**
   (для потоков под управлением control API).
5. Если задан `?c=<uuid>` — регистрирует соединение для реконсиляции.
6. Отдаёт снимок, затем в цикле льёт живые чанки.

**Ответ:** `200`, `Content-Type: video/mp2t`, `Cache-Control: no-store`, тело —
бесконечный поток TS. `404`, если поток не зарегистрирован.

**Защита от «залипших» зрителей:** каждая запись ограничена дедлайном `-write-timeout`
(по умолчанию 15 с). Зритель, переставший вычитывать сокет без честного закрытия
(свёрнутый плеер, оборвавшийся мобильный канал), сбрасывается — иначе он навсегда
заблокировал бы горутину раздачи. Подробнее — [04, «Защита от залипших зрителей»](04-internals.md#защита-от-залипших-зрителей).

### `GET /hls/<id>/index.m3u8` — плейлист HLS

Возвращает текущий медиаплейлист, сгенерированный в памяти. Обработчик —
[`serveHLS`](../../internal/server/server.go).

- Если сегментов ещё нет — `404 no segments yet`.
- **Ответ:** `200`, `Content-Type: application/vnd.apple.mpegurl`, `Cache-Control: no-store`.
- URI сегментов в плейлисте — относительные `<seq>.ts`.

### `GET /hls/<id>/<seq>.ts` — HLS-сегмент

Возвращает байты сегмента с номером `<seq>`.

- Если сегмент уже уехал из скользящего окна — `404`.
- Если для потока задан ключ шифрования — сегмент отдаётся **AES-128-CBC-зашифрованным**,
  иначе plain.
- **Ответ:** `200`, `Content-Type: video/mp2t`.

> HLS **опросный** и не держит «ссылку» на поток (ref). Каждый запрос HLS обновляет
> метку доступа, чтобы источник не остановился под HLS-only аудиторией — см.
> [05. Жизненный цикл](05-lifecycle.md).

### `GET /healthz` — health-check

Всегда `200` с телом `ok`. Для мониторинга/keepalive.

## Управляющая поверхность (только для PHP)

Включается флагом `-ctl`. Роутинг — [`ControlHandler`](../../internal/server/server.go).
Сюда ходит **только PHP-панель**.

| Метод и путь | Назначение |
|--------------|------------|
| `PUT`/`POST` `/streams/<id>` | Зарегистрировать/обновить **pull**-источник. |
| `GET /streams/<id>` | Статус потока (off-air-детекция). |
| `DELETE /streams/<id>` | Снять поток, остановить puller/ingest. |
| `PUT`/`POST` `/ingest/<id>` | Перевести поток в **push**-режим, вернуть путь сокета. |
| `DELETE /ingest/<id>` | Снести push-поток. |
| `GET /probe/<id>?wait=<ms>` | Прогреть источник и дождаться данных. |
| `GET /connections` | Все uuid активных live-TS зрителей. |
| `GET /rates` | Средняя скорость отдачи на зрителя (КБ/с), по uuid. |
| `POST /signal/<uuid>` | Поставить в очередь одноразовый оверлей-баннер «отправить сообщение» одному зрителю. |

### `PUT` / `POST` `/streams/<id>` — регистрация pull-источника

Регистрирует источник, который демон будет тянуть **сам**. Тело — JSON:

```json
{
  "urls":   ["http://src1/live.ts", "http://src2/..."],
  "ua":     "Mozilla/5.0",
  "proxy":  "host:port",
  "cookie": "...",
  "ffmpeg": "/usr/bin/ffmpeg",
  "chunk":  12032,
  "key":    "<hex 16 байт, опц.>",
  "iv":     "<hex 16 байт, опц.>"
}
```

| Поле | Обяз. | Смысл |
|------|:----:|-------|
| `urls` | да | Кандидатные URL источника, пробуются по порядку. Пустой список → `400 bad config`. |
| `ua` | нет | User-Agent запроса к источнику. |
| `proxy` | нет | HTTP-прокси `host:port`. |
| `cookie` | нет | Значение заголовка `Cookie`. |
| `ffmpeg` | нет | Путь к ffmpeg (для ремукса не-mp2t источников). |
| `chunk` | нет | Размер чтения ingest (выравнивается вниз до 188). |
| `key`, `iv` | нет | Hex по 16 байт — включают шифрование HLS. TS fan-out всегда plain. |

Если зрители уже ждут этот поток — puller стартует немедленно. **Ответ:** `204 No Content`.

### `GET /streams/<id>` — статус потока

Отдаёт JSON, достаточный для PHP-авторизации, чтобы решить вопрос off-air:

```json
{
  "running":       true,
  "refs":          3,
  "has_data":      true,
  "since_data_ms": 120
}
```

| Поле | Смысл |
|------|-------|
| `running` | Puller запущен. |
| `refs` | Сколько live-TS зрителей подключено сейчас. |
| `has_data` | Был ли хотя бы один непустой чанк данных. |
| `since_data_ms` | Миллисекунд с последнего непустого чанка; `-1`, если данных не было. |

«`running=true`, но `has_data=false` или большой `since_data_ms`» = источник мёртв → PHP
показывает страницу «not on air». `404`, если поток не зарегистрирован.

### `DELETE /streams/<id>` — снять поток

Сбрасывает конфиг, останавливает puller, закрывает ingest-listener, удаляет поток из
реестра. **Ответ:** `204`.

### `PUT` / `POST` `/ingest/<id>` — push-режим

Переводит поток в режим, где **продюсер сам пушит** данные демону (например, ffmpeg-tee
потока). Тело опционально:

```json
{ "chunk": 12032, "key": "<hex, опц.>", "iv": "<hex, опц.>" }
```

Демон поднимает per-stream unix-listener и возвращает путь сокета, к которому должен
подключиться продюсер:

```json
{ "socket": "/home/xc_vm/bin/xc_fanout/sockets/ingest/<id>.sock" }
```

Вызывается панелью (`StreamProcess`) **перед** запуском ffmpeg-tee. `key`/`iv` так же
включают шифрование HLS. **Ответ:** `200` с JSON выше.

### `DELETE /ingest/<id>` — снести push-поток

То же, что `DELETE /streams/<id>` (общий `Unregister`). **Ответ:** `204`.

### `GET /probe/<id>?wait=<ms>` — off-air-прогрев

Прогревает зарегистрированный поток (запускает puller, как это сделал бы зритель) и
ждёт появления данных, затем возвращает тот же JSON, что `GET /streams/<id>`.
Обработчик — [`serveProbe`](../../internal/server/server.go).

| Параметр | По умолчанию | Максимум | Смысл |
|----------|:-----------:|:--------:|-------|
| `wait` | 5000 | 30000 | Сколько миллисекунд ждать первых данных. |

PHP вызывает это после регистрации proxy-источника: если по истечении `wait` данных нет
(`has_data=false`) — показывает «not on air», вместо того чтобы зритель завис на мёртвом
источнике. Прогретый puller продолжает работать, так что реальное соединение зрителя
подхватывается к нему; если зритель не пришёл — рипер остановит puller.

### `GET /connections` — реконсиляция зрителей

Возвращает JSON-массив uuid **всех** сейчас подключённых live-TS зрителей (значения
`?c=`) по всем потокам. Обработчик — [`serveConnections`](../../internal/server/server.go).

> uuid дедуплицируется **в пределах одного потока** (refcount на подключение). Глобальной
> дедупликации по потокам нет: один и тот же uuid, подключённый к двум разным потокам,
> теоретически попадёт в список дважды. На практике `?c=` уникален на соединение
> (`md5(uniqid())` на каждый auth-запрос), так что это безвредно.

Демон `fanout_sync` сверяет этот набор со строками `lines_live` и закрывает те, чей uuid
здесь уже не числится — потому что под X-Accel PHP не видит отключение зрителя сам.

**Ответ:** `200`, `Content-Type: application/json`, тело — например `["uuid-1","uuid-2"]`.

### `GET /rates` — телеметрия скорости зрителей

Возвращает JSON-объект: для каждого активного live-TS зрителя его uuid → **средняя скорость отдачи
в КБ/с** с момента подключения (`bytes / elapsed / 1024`). Обработчик —
[`serveRates`](../../internal/server/server.go); он суммирует байты, реально записанные демоном в
каждое соединение `?c=<uuid>`.

Это замена легаси-цикла дочитывания в `live.php`, который сам измерял ту же скорость и писал её в
`DIVERGENCE_TMP_PATH/<uuid>`. Под X-Accel PHP вне байтового тракта и больше её не видит, поэтому
демон `fanout_sync` опрашивает этот эндпоинт, сравнивает каждую скорость с ожидаемым битрейтом
потока (`streams_servers.bitrate / 8 * 0.92`) и записывает отставание как `divergence` зрителя в
`lines_live` / `lines_divergence` (ADR 0003, P4). Если uuid вдруг активен на нескольких потоках —
берётся бо́льшая скорость.

> Поскольку демон **отбрасывает** отстающего зрителя (вытеснение медленного подписчика + дедлайн
> записи), устойчиво низкая скорость здесь почти не появляется — средняя у здорового realtime-зрителя
> сходится к битрейту потока, так что divergence у демон-зрителей обычно ~0. Значение — это сигнал
> скорости соединения и отображение в админке, а не проверка «быстрого слива» (зритель не может
> тянуть быстрее, чем живой хвост раздаётся fan-out’ом).

**Ответ:** `200`, `Content-Type: application/json`, тело — например `{"uuid-1":512,"uuid-2":498}`.

### `POST /signal/<uuid>` — оверлей «отправить сообщение»

Ставит в очередь **одноразовый** текстовый баннер, который будет выжжен в видео единственного
зрителя с uuid соединения `<uuid>` (значение `?c=`). Это замена легаси-оверлея из байтового тракта
PHP, убранного в фазе E, — админская функция «Отправить сообщение». Панель постит его через
[`FanoutClient::sendSignal`](../../../XC_VM/src/Streaming/Fanout/FanoutClient.php); обработчик —
[`serveSignal`](../../internal/server/server.go). Тело — JSON:

```json
{
  "message":     "Ваша подписка истекает завтра",
  "font_size":   24,
  "font_color":  "white",
  "xy_offset":   "150x110",
  "ttl":         30
}
```

| Поле | Обяз. | Значение |
|------|:----:|-------|
| `message` | да | Текст для отрисовки. Экранируется для ffmpeg `drawtext` (без shell). Пусто → `400`. |
| `font_size` | нет | Размер шрифта (по умолчанию 24). |
| `font_color` | нет | Цвет ffmpeg — имя (`white`) или `#RRGGBB`, опц. `name@0.8`. Санитизируется; невалидный → `white`. |
| `xy_offset` | нет | Позиция как `"<x>x<y>"`. Отсутствует/битый → случайная позиция (150–380 × 110–250). |
| `ttl` | нет | Секунды, сколько сигнал в очереди валиден, пока не истёк непоказанным. `0`/отсутствует = без срока. |

**Как потребляется** (best-effort, одноразово, и **никогда** не ломает воспроизведение):

- **HLS** (`serveHLS`): следующий сегмент, запрошенный с совпадающим `?c=<uuid>`, перекодируется в
  памяти с баннером `drawtext`; при любой ошибке ffmpeg отдаётся обычный сегмент.
- **Live TS** (`serveLive`): баннер выжигается на короткое (~5 с) переходное окно — свежий
  clean-join снапшот пере-затравливает пер-зрительский ffmpeg, затем зритель возвращается к сырому
  fan-out.

Оба потребителя передают `?vc=<codec>` (видеокодек источника, прокинутый `live.php`), чтобы
перекодирование сохранило кодек потока; отсутствует → `h264`. Требует запуска демона с `-ffmpeg`
**и** `-font`, указывающими на ffmpeg с фильтром `drawtext`, — без них сигнал становится no-op.
**Ответ:** `204 No Content` после постановки в очередь (`400` при пустом сообщении, `405` на не-POST).

## Сводная таблица кодов ответов

| Ситуация | Код |
|----------|-----|
| Успешная раздача / статус / плейлист / сегмент | `200` |
| Успешная регистрация/удаление на control | `204` |
| Поток не найден / сегмента нет / нет сегментов | `404` |
| Пустой `urls` в `/streams` | `400 bad config` |
| Неверный метод на control-эндпоинте | `405` |
| Ошибка поднятия ingest-сокета | `500` |
